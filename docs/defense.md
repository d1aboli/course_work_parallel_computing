# Підготовка до захисту

## Демонстрація (≈5 хв)

1. `docker compose ps` — чотири сервіси: `dataset-init` і `ollama-init` завершились, `ollama` і `search-server` (healthy).
2. `curl localhost:8080/api/health` → `{"status":"ok","ollama":true,...}`.
3. Web UI → «Індекс і статистика» → 1 потік, потім 12 потоків: ~10 с проти ~2 с, показати `phases`.
4. Пошук `sherlock holmes` з LLM: три етапи, сині терми моделі, підсвічування; той самий запит без LLM (2 мс).
5. `./search --expand "storm at sea"` — CLI.
6. Графіки `report/figures/index_scaling.png`, `index_partitions.png`, `throughput_llm.png`.
7. UML: `docs/uml/*.png`; коміти: `git log --oneline`.

## Відповіді на теоретичні питання (додаток Б силабусу)

1. **Процес** — програма, що виконується, з власним віртуальним адресним простором, дескрипторами файлів і хоча б одним потоком. У нас: JVM у контейнері `search-server` — один процес.
2. **Потік** — послідовність виконання всередині процесу; потоки ділять купу, але мають власні стек і регістри. У нас: робочі потоки `ThreadPool` (`index-N`, `http-N`, `ws-N`), потік `acceptor`.
3. **Віртуальний адресний простір** — відображення адрес, які бачить процес, на фізичну пам'ять, що його підтримує ОС за допомогою MMU і таблиць сторінок; ізолює процеси один від одного.
4. **Складові**: код (text), дані й BSS, купа, стеки потоків, відображені файли та бібліотеки, ядрова частина. У JVM купа Java — це регіон у купі процесу (`heap_committed_mb` у `/api/stats`).
5. **Фізична й віртуальна адреса**: віртуальну генерує програма, фізичну — MMU після трансляції через таблиці сторінок (з TLB); одна віртуальна сторінка може бути не завантажена (page fault).
6. **Стек між потоками**: кожен потік отримує окремий стек фіксованого розміру (у JVM `-Xss`, типово 1 МіБ віртуальної пам'яті), локальні змінні в стеку приватні, об'єкти — у спільній купі. Тому локальна `HashMap` задачі в `Indexer.mapBatch` не потребує синхронізації, а спільний `PartitionedIndexBuilder` — потребує.
7. **Стан гонки** — результат залежить від порядку виконання потоків, які звертаються до спільних даних і хоча б один пише. Приклад, якого немає в коді: два потоки виконують `map.get` + `put` для одного терма одночасно → втрата входжень.
8. **Взаємне блокування** — кожен з потоків чекає ресурс, утримуваний іншим (умови Коффмана: взаємне виключення, утримання й очікування, відсутність витіснення, кругове очікування).
9. **Як запобігаємо**: дані задачі приватні (`BatchTermTable`); партицію змінює лише власник, власність через `AtomicBoolean.compareAndSet` (`PartitionedIndexBuilder.drain`); у `StripedIndexBuilder` потік тримає не більше одного замка — немає кругового очікування; готовий індекс незмінний і публікується через `AtomicReference`; доведено тестами `IndexBuilderTest` (порівняння з послідовним еталоном) і `IntegrationTest.concurrentClientsGetConsistentResults`.
10. **Механізми синхронізації**: м'ютекс/`ReentrantLock`, умовні змінні (`Condition`), семафори (`Semaphore` у `QueryExpander`), бар'єри й засувки (`CountDownLatch`, `CyclicBarrier` у тестах), атомарні змінні та CAS, volatile, `Future`.
11. **Як працюють**: замок — атомарна операція над станом у пам'яті (CAS), при невдачі потік паркується в черзі очікування ОС/JVM; `Condition.await` атомарно відпускає замок і засинає, `signal` будить; семафор — лічильник дозволів; volatile/атомарні дають порядок пам'яті (release/acquire, happens-before у JMM).
12. **Перевага неблокуючих**: потік ніколи не засинає на структурі, немає взаємних блокувань і інверсії пріоритетів, затримка одного потоку не зупиняє інших. Але (наш експеримент з 1 партицією) неблокуючий алгоритм не робить послідовну роботу паралельною: очікування 0 с проти 22,4 с, а час побудови той самий.
13. **Чому немає гонки**: зміна стану — одна атомарна інструкція CAS (`lock cmpxchg` на x86): «записати нове значення, якщо поточне дорівнює очікуваному». Якщо інший потік встиг змінити — CAS повертає false, і ми повторюємо (`TreiberStack.push`) або йдемо далі (`busy.compareAndSet` → hand-off).
14. **Міжпроцесна взаємодія**: сокети (TCP/UDS), канали (pipe), спільна пам'ять, черги повідомлень, сигнали, файли. У нас: TCP між `server` і `ollama`, сигнал SIGTERM від `docker stop`.
15. **Сокет** — кінцева точка двостороннього зв'язку, ідентифікована (IP, порт, протокол); у нас `ServerSocket.accept()` у `HttpServer.acceptLoop`, клієнтські сокети в `Bench`.
16. **IP і порт**: IP-адреса ідентифікує мережевий інтерфейс (у Compose — DHCP/IPAM Docker-мережі, ім'я `ollama` резолвить вбудований DNS), порт — застосунок на вузлі: серверний задаємо (8080, 11434), клієнтський — ефемерний від ОС.
17. **Хеш-таблиця** — масив кошиків, індекс = хеш(ключ) mod розмір; пошук/вставка O(1) в середньому, O(n) у найгіршому. У нас: `BatchTermTable` — відкрита адресація з лінійним зондуванням, заповнення ≤ 0,5.
18. **Структура з паралельним записом**: розщеплення замків (`StripedIndexBuilder`), неблокуючі CAS-структури (`TreiberStack`), розбиття на партиції з власником (`PartitionedIndexBuilder`), локальні копії + злиття (map-reduce у `Indexer`).
19. **Інвертований індекс** — відображення терм → список документів (+ частоти); у нас `InvertedIndex`: 64 партиції, `HashMap<String, long[]>`, posting = (docId << 32 | tf).
20. **Прискорення**: S(p) = T₁ / Tₚ, ефективність E = S / p; межа — закон Амдала 1/(f + (1−f)/p); експериментальна частка Карпа — Флатта e = (1/S − 1/p)/(1 − 1/p). У нас S(10) = 4,85, f ≈ 0,125.
21. **Query expansion** — доповнення запиту синонімами/пов'язаними словами для підвищення повноти (знайти документи без точного слова). У нас — Ollama `qwen2.5:1.5b`, вага термів моделі 0,4.
22. **REST vs WebSocket**: REST — запит-відповідь поверх HTTP, без стану між запитами; WebSocket — постійне двостороннє з'єднання після HTTP Upgrade, сервер сам надсилає повідомлення (у нас — етапи конвеєра по мірі готовності).
23. **Docker / Compose**: Docker — ізольовані контейнери з образів (namespaces, cgroups), Compose — опис багатоконтейнерної системи одним YAML і запуск `docker compose up`. Потрібні для відтворюваного розгортання сервера, моделі й даних.
24. **Паралельна обробка HTTP**: пул потоків (у нас 64 HTTP-потоки, з'єднання обслуговується потоком упродовж keep-alive), або подієвий цикл (NIO/epoll), або віртуальні потоки; довгі операції — в окремий пул (у нас WebSocket-сеанси).
25. **Пул потоків** — заздалегідь створені потоки і черга задач: немає витрат на створення потоку на кожну задачу, обмежується паралельність, задачі балансуються. У нас `core/ThreadPool`: `ReentrantLock` + `Condition`, `submit` → `Future`, graceful `shutdown`.
